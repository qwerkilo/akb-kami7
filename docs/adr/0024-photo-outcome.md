# ADR-0024：照片结果的单一出处（原因在产生处写一次，报告是投影）

- Status: accepted（2026-10-06）
- 相关：ADR-0022（照片身份）、ADR-0023（照片冻结）；`CONTEXT.md` 的「照片回退链」词条

## 背景

「为什么这位成员没有照片」曾经有三条独立通道、两种键空间、两段报告：

- `photo_chain` 用 `errors: list[Exception]` 收请求失败（可选参数；`love_members` 不传，
  `cdx_rows`/`wayback_photo` 连参数都没有）；
- `morningmusume_members` 把 errors 翻成 `notes: dict[file → 中文原因]`（5 种原因）；
- `fetch_members` 又开 `failures: dict[id → 中文原因]`（3 种原因）。

键空间不同（成员身份 `file` vs 照片文件身份 `id`），优先级靠链尾的 `setdefault` 竞争，
报告分两段（「未解析到」+「取不下来」）—— 两段的并集等于缺图名单**只在当前数据下成立**
（48G/等爱今天没有缺图者；`--no-dl` 下缓存缺失者也不进第二段）。

工单 09/10 在这上面打过两轮补丁（截断三分类、下载/压缩失败进汇总），补丁越多越说明
语义该由链自己拥有。第五轮架构扫描的候选 7 记录了这条（报告：
`/tmp/opencode/architecture-review-20261006-104242.html`）。

## 决定

1. **链的每一节产出同一个结果形状**：`(url, reason)` —— 成功给 url，落空给原因
   （`查询失败` / `源里没有`）。原因在**产生处写一次**，不再经过 `errors` 列表中转。
2. **结果表由管线拥有**：loader 把原因交出来（不再自己打印汇总），`fetch_members.main`
   合并「解析阶段的原因」与「下载/压缩阶段的失败」，**只打一份报告**。
3. **报告按成员索引**（`file`）：`id` 是照片文件的存储细节，合并处映射一次。
4. **原因保持中文诊断文本**，不做成领域枚举 —— 它是给管线操作者看的诊断，不是站点概念
   （YAGNI；将来真要多语言再结构化）。
5. 解析时的逐人 warn 行与最终报告重复 → **只留最终报告**（一条信息一次）。

## 后果

- 「缺图名单」与「原因表」同源：报告覆盖的成员集合 == 缺图名单，**结构性成立**，
  不再是「当前数据下成立」。
- `love_members` 的缺图者也有原因（此前它的缺图者是「未记录」）。
- `cdx_rows` / `wayback_photo` 的失败仍会落成「源里没有」（旧站候选枚举失败没有单独分类）
  —— 已知限制，不在本决定范围。
- 守卫可以钉「一份报告、按成员、集合相等」，不必再钉两段格式。

## 被否的方案

- **结构化枚举 + 打印处翻译**：诊断文本不是领域概念，改 11 处测试换不来真实收益（YAGNI）。
- **结果表放进 `photo_chain`**：`photo_chain` 不知道成员与团，它只该返回 `(url, reason)`；
  合并的职责在知道全貌的那一层（管线）。
