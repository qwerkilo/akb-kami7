# 05 · CI / E2E 负载画像

- **票**：`.scratch/perf-load/issues/05-ci-e2e-load.md`
- **日期**：2026-10-30
- **口径**：只读研究。**未跑任何 E2E**，未改产品代码，未 commit。所有 CI 数字来自 GitHub Actions 的 run/job/step 时间戳；所有本地数字来自现有日志。

## Question

本地 `e2e:all` ~4.5 分钟、CI 只跑三个快速套件、矩阵套件 nightly：当前 CI 分钟数与反馈延迟的构成是什么？
哪些等待/重复加载/套件矩阵可以合并、分片或缓存而不降覆盖？给出成本与风险，不实施。

拆成四问：

1. 本地 `e2e:all` 的墙钟构成（各套件、启动/清理、并行度）；CI 三个快速套件与 nightly 矩阵的分钟数与反馈延迟；哪些是实测、哪些是推断。
2. 哪些等待/重复加载/矩阵状态可以合并、分片或缓存而不降覆盖（每状态 goto+reload、字体等待、套件并行度、浏览器缓存）。
3. 每项的预计节省、CI 分钟成本、风险（覆盖、flake、内存）；明确不建议做的项。
4. 对 push 闸门与 nightly 分别给建议。

## Method

1. 读配置与编排：`.github/workflows/{check,matrix,freshness}.yml`、`package.json`、`e2e/run-all.cjs`、`e2e/_suite.cjs`、`e2e/_check.cjs`、`e2e/_wait.cjs`、`e2e/_store.cjs`、`e2e/_ui.cjs`、`e2e/verify-header.cjs`、`e2e/verify-first-screen.cjs`、`e2e/e2e-pwa.cjs`、`e2e/e2e.cjs`。
2. 解析本地日志：`/tmp/akb-e2e-logs/{e2e,first,header,v5,pwa}.log`（2026-10-30 13:44–13:49 一轮的套件日志，含逐 check 的 `[NmSs]` 时间线）与 `/tmp/opencode/e2e-all-*.log`（2026-10-06..10-30 的 run-all 汇总日志）。
3. 读历史记录：`docs/reviews/checkpoints/2026-10-06..07-perf-scans.md`、`2026-10-08-scans6-7.md`、`2026-10-08..11-ux-perf.md`、`docs/reviews/checkpoints.md`（未收口清单）、`.scratch/optimize-2026-10/issues/03-ci-matrix-nightly.md`。
4. CI 运行记录：本机 `gh` 未安装；用 GitHub REST（只读）经 `https://gh-proxy.com/` 前缀取：
   - `actions/workflows/check.yml/runs?per_page=10` → check #100–#109；
   - `actions/runs/41066590788/jobs` → #109 的 check/e2e 两个 job 与全部 step 耗时；
   - `actions/runs/40967113707/jobs` → matrix #3 的 header/first step 耗时；
   - `actions/runs/40531957336/jobs`、`actions/runs/40878932019/jobs` → 两次失败 run；
   - `actions/workflows/matrix.yml/runs?per_page=20` → matrix #1–#4；
   - `actions/jobs/124099375299/logs` → #109 e2e job 的原始日志（确认 pwa 的字体预热行）。
5. 静态计数：`goto/reload/newContext/waitForTimeout` 调用点、固定等待的算术和、矩阵状态数（由各套件 `expect` 与循环维数交叉核对）。
6. **没做**：没跑 `npm run e2e*`；没做本地 A/B；没改任何 `e2e/*.cjs` 或产品代码；没上传/提交。

测量口径：

- “墙钟”= job/run 的 `started_at`→`completed_at`（CI）或 run-all 的 `汇总：… 总耗时`（本地）。
- “套件耗时”= run-all 的 `✓ [name] · Xs`；套件内部耗时=日志里最后一个 `[NmSs]` 减去第一个（不含进程退出，误差 <1s）。
- “固定等待”= 源码里 `waitForTimeout(<字面量>)` 在每个状态/每次迭代必然执行的时长；循环放大的部分单独说明。
- 本地 2026-10-30 的 run-all 都是 **2 并发**（可用内存 3431–5489MB，`pickParallel` 的 3000–6000 档）；这是当前默认，不是特意压测。

**A3. pwa 的 31 秒字体等待（实测，且是当前最大的单项浪费）**

`/tmp/akb-e2e-logs/pwa.log`（2026-10-30 13:49 结束）：

```
[0m08s] PASS  在线时已加载 16 张照片
…等待字体预热 5s（12 条）
…等待字体预热 10s（12 条）
…等待字体预热 15s（12 条）
…等待字体预热 21s（12 条）
…等待字体预热 26s（12 条）
…等待字体预热 完成 31s（12 条）
· 断网前字体缓存：12 条（其中 CSS 2 条）
```

代码（`e2e/e2e-pwa.cjs:236-242`）：

```js
for (let i = 0; i < 60; i++) {
  gotFonts = await fontCacheInfo();
  if (gotFonts.css > 0 && gotFonts.n >= 17) break; // ← 17
  fontTick.tick(`${gotFonts.n} 条`);
  await page.waitForTimeout(500);
}
```

当前稳态是 **12 条**（CSS 2 + woff2 10），阈值 **17 永远不满足** → 循环跑满 `60 × 500ms = 30s` 才退出。CI 上同样如此：`actions/jobs/124099375299/logs` 里 pwa 的 5/10/15/20/25/完成 30s 行，缓存同样是 12 条（CSS 2）。这不是“等得久”，是**门恒假**。

历史对照（同一台机器）：

| 时间                      |           pwa 总耗时 |        字体缓存条数 | 日志                                                          |
| ------------------------- | -------------------: | ------------------: | ------------------------------------------------------------- |
| 10-27/29 旧轮次           |               30–32s |            50–52 条 | `e2e-all-payload.log` / `e2e-all-share.log` + 旧 pwa 日志片段 |
| 10-30 11:32（改版前）     |              **25s** |              未记录 | `e2e-all-tm2.log`                                             |
| 10-30 12:52（改版工作区） | **57s**（pwa 44/45） | 12 条（13:44 日志） | `e2e-all-award1.log`                                          |
| 10-30 13:39               |              **54s** |               12 条 | `e2e-all-award5.log`                                          |

10-30 12:52 起的改版工作区（`ac4d636`，12:54 提交；classic：系统衬线大标题等）里，pwa 从 25s 涨到 54–57s，增量正好是这 30s。旧轮次缓存 50–52 条时，`n>=17` 很快满足（pwa 30s 左右）。**阈值 17 是旧字体用量的一份硬编码副本；改版把 warm set 缩到 12 后它失效了。** 这与 AGENTS.md 的“陈述当前状态的数字不要写”是同一条教训。

## Findings

### F1. 本地 `e2e:all` 的关键路径是 e2e → v5 → pwa，first/header 是影子工作

13:39 轮：177 + 25 + 54 = 256s，正好等于总墙钟；first+header 的 221s 链在 3m41s 结束，早于 pwa 的 4m16s。**优化 header/first 不会缩短本地 `e2e:all`**（除非把并发提到 3）。本地要见效，优先 pwa（30s 恒假门，直接减总墙钟）和 e2e 主套件；header/first 的优化只对 nightly 有意义。

### F2. push 闸门实际是 ~3m35s；check job 只有 38s，不是瓶颈

成功的 7 次 run 中位数 215s；#109 的 e2e job 234s，check 38s，两者并行。**push 反馈延迟由 e2e job 决定**，而 e2e job 的 57% 是主套件、21% 是 pwa、12% 是 setup。check job 的 `npm run check` 只有 16s，优化它没有反馈价值。

### F3. pwa 的 30 秒字体等待是“门恒假”，是当前最大的低风险单项

阈值 `n>=17`（`e2e/e2e-pwa.cjs:238`）与当前 warm set 12 条不一致；本地和 CI 都跑满 30s。10-30 改版前 pwa 25–30s，改版后 54–57s，增量正好这 30s。修掉它：本地 `e2e:all` 4m16→~3m47，CI e2e job 234→~205s，push 墙钟 -30s。**这是唯一一个“只改测试、不降覆盖、立即见效”的项。**

### F4. nightly 矩阵实际 3m05–3m50（中位 ~3m25）；“runner 慢 10–20×”的注释是陈旧数字

matrix #1–#4 的 run 墙钟 205/185/205/230s；#3 的 job 201s（setup 27 + header 105 + first 68），#4 的 job 226s（setup 53 + header 105 + first 64）。本地 header 122s / first 103s，CI 反而更快。**“runner 上比本地慢 10–20×”至少对 header/first 不成立。** 2026-10-08 的 >2h 事件是全量 `e2e:all`（5 套件、`pickParallel` 在 runner 上可能选 4 并发）造成的，不是矩阵套件本身的固有成本；当时没有 step 级数据，结论是推断。这个陈旧数字直接导致了“矩阵不能进 push”的决策，应该更新。

### F5. header/first 的耗时主要是固定 sleep，不是渲染

CI 上 header 105s 里 90s 是 `1200+300+2×500ms` × 36 个状态；first 68s 里 43.2s 是 600ms × 72 个状态。**两者合计 133s 的固定等待，占 173s 套件时间的 77%。** 这意味着：

- 矩阵套件在更快的 runner 上不会按比例变快（setTimeout 不走 CPU）；
- 用条件等待（`document.fonts.ready`、`.card`、offline chip 稳定）替代是有效的；
- 反过来说，**“runner 慢 10–20×”与固定等待的算术矛盾**——如果是 10–20×，header 不可能是 105s（本地 122s）。

### F6. 主套件 390px 的第二组循环没有真的切语言：3 次都是 zh，标签却写 zh/en/ja

`e2e/e2e.cjs:2003-2014`：

```js
for (const lang of ["zh", "en", "ja"]) {
  const narrow = await browser.newContext({ viewport: { width: 390, ... }, locale: "zh-CN" });
  ...
  await np.goto(BASE, ...);
  await np.waitForTimeout(1500);
  for (const target of ["love", "48g"]) { ... }
}
```

循环体里没有任何 `setLang` / `keyboard.press`；`locale` 固定 `zh-CN`，`lang` 只用在检查标签上。**这 3 次是重复的 zh 状态，不是语言矩阵。** 后果：

- 2 次多余的整页加载（CI 约 5s、本地约 10s）；
- push 闸门的“390px tab 可达”实际只覆盖 zh；en/ja 的 tab 可达只有 nightly 的 header 套件覆盖（header 是 3 语言 × 3 档 × 4 系列 × 在线/离线）。
- 这不是“可以合并的等待”，而是**先要修的覆盖缺陷**；修完会多花 ~5–10s，不是省时间。第一组循环（`1902-2001`）是真的按语言切的（`keyboard.press` 在 1928），所以“首屏见脸”的语言维是真的。

### F7. setup 占 e2e job 的 12%，且有一个 552s 的环境长尾

正常 setup 28–53s（Playwright install 17–42s）；#102 的 install 552s，把 run 拉到 701s。**缓存 Playwright 浏览器是唯一能同时降低常态成本和长尾风险的项**；它不影响任何覆盖。

### F8. 失败路径会跳过 v5/pwa，反馈快但覆盖不完整

#104/#102 的 `npm run e2e` 失败后，step 9/10（v5/pwa）都是 skipped。失败反馈约 2m42s（#104 162s），比成功路径快；但一次红 run 不会告诉你 v5/pwa 是否也坏了。这是“快速失败”的合理取舍，不是缺陷，但在统计 flake/回归时要记得。

### 明确不建议做

1. **CI 上跑全量 `e2e:all`**。2026-10-08 已实测 >2h（`f50c2f5`）；`run-all` 的 `pickParallel` 只看可用内存，runner 上可能选 4 并发，4 个 Chromium 在 runner 上会互相拖死。当前三套件串行是正确取舍。
2. **给 nightly 分片/拆 job**。201s 的 job 在 60 分钟 timeout 下非常宽裕；拆分会增加 setup（27s/job）且没有反馈收益。矩阵要拆，唯一理由是“进 push 后想缩短关键路径”，不是 nightly 本身。
3. **削减矩阵维度**：first 的 6 个宽度（320/360/375/390/414/560）、2 皮肤、2 档；header 的 3 语言 × 3 档 × 4 系列 × 在线/离线。这些维度各自对应历史 P0（≤380 换行、en 16 档品牌宽、离线胶囊），删一个就是降覆盖。
4. **把“重新排序”6 次降到 4 次**。6 次是为了把“resort 没洗牌”的假红概率从 ~0.5% 降到 ~0.01%（`e2e.cjs:511-513`）；省 ~6s，换 flake 风险，不值。
5. **整体删等待 / 加自动重试**。`run-all` 明确不重试（flake 要看得见）；固定等待里有一部分是真实的交互稳定窗口，粗暴替换会变成 flake 工厂。
6. **CI 上 3–4 并发**。没有 runner CPU/内存数据；2 并发已经是需要试跑验证的改动。

## 对 push 闸门与 nightly 的建议

### push 闸门

**现状**：check 38s + e2e 234s 并行，墙钟中位数 3m35s，范围 3m22–3m58s。这个延迟对“每次 push 都跑”是合适的，不需要为了速度牺牲覆盖。

**建议顺序**：

1. **O1（pwa 字体门）**：-30s，零覆盖风险，先做。
2. **O2（Playwright 缓存）**：-15s 常态，消除 552s 长尾；先钉 Playwright 版本再缓存。
3. **O3（2 并发）**：如果试跑稳定，-72s，把 push 墙钟压到 ~2m45s。这是可选的；不做也已经是 3m35s。
4. **O8（390px 语言修正）**：覆盖修正优先于省时；修完 push 的 en/ja tab 可达才是真的。
5. **O9（矩阵进 push）**：**不建议无条件做**。它加 201–226s runner/次而墙钟不变（e2e 仍是关键路径）；只有在“矩阵覆盖必须挡 push”这个产品决策下才做，且应先做 O5/O7 把矩阵降到 ~115s，或 path-filter 到 UI 文件。当前 nightly 已经覆盖完整矩阵；push 的缺口至少包括 en/ja 的 390px tab 可达（O8 可补），但不止这一项。

### nightly

**现状**：matrix job 201–226s（setup 27–53 + header 105 + first 64–68），run 185–230s（中位 ~205s）；cron 18:00 UTC 但实际 ~22:00 UTC 才创建（GitHub 调度延迟 ~4h）。60 分钟 timeout 非常宽裕。

**建议**：

1. **保持每日 + 手工触发**，不要分片/拆 job；成本 ~3.4–3.8 min/天，收益是 CSS/布局回归的每日兜底。
2. **更新 `matrix.yml` 的陈旧注释**：把“runner 上慢 10–20× / 全量 >2h”改成实测的 “header 105s / first 64–68s / job 201–226s”；否则下一个人还会基于错误数字做决策。
3. **O5 + O7** 把矩阵从 201–226s 降到 ~115s。这不是为了 nightly 本身（它已经很快），而是为了让“矩阵进 push”或“PR 上跑矩阵”变得便宜。
4. 如果矩阵进 push，nightly 可以保留为兜底（每天 3.4 min 很便宜），也可以降为每周；不建议直接删——它是数据/视觉漂移的最后一道网。

## Caveats

- **CI runner 规格未知**。GitHub 的 `ubuntu-latest` 在不同仓库可见性/计划下可能是 2 或 4 vCPU、7 或 16GB；本报告的所有 CI 数字是墙钟，不是 CPU/内存画像。O3/O4 的并发建议必须用 `workflow_dispatch` 实测，不能按本地 15GB 的直觉推。
- **样本量**：push 成功 7 次、nightly 4 次、失败 3 次。10-30 的视觉改版（`ac4d636`）会改变布局/字体，旧轮的套件耗时不能直接外推；nightly #4（10-30，230s）是新代码首跑，已单独列出。
- **“10–20×”的出处是注释/检查点，不是受控测量**。本报告的 CI 实测（header 105s、first 68s）与它矛盾；>2h 事件的根因（5 套件 × 4 并发）是推断，因为没有 step 级日志。不要把“10–20×”继续当事实引用。
- **本地测量不是交替 A/B**。run-all 的 2 并发由可用内存决定（3431–5489MB），不同轮次的内存/后台负载不同；3m44–4m21 的范围应视为噪声带，不要拿单次 4m16 与单次 3m44 做因果结论。
- **pwa 字体条数可能随浏览器/Google Fonts CSS 变化**。修 O1 时不要把 17 换成另一个硬编码数字；最好从产品的 warm set 派生（`core` 的 `fontUsages`/`warmUrls` 或页面暴露的计数），并保留离线 face/宽度断言作为正面防线。若用固定上限，给 10–15s 余量并在未达标时打日志（不要静默）。
- **header 36→9 会改变“每系列冷加载”的语义**。header 的目的是页头几何，不是冷启动；但为了不丢“冷加载下系列 tab 仍可达”的保证，建议保留每个语言至少 1 次冷加载 + 4 系列页内切换，或在主套件里补一条冷加载系列检查。
- **390px 第二组循环的语言 bug 是覆盖缺陷，不是纯负载问题**。修它可能净省时为 0（甚至多花 5–10s）；不要把它当成“合并等待”的省时项。
- **计费**：GitHub Actions 对公开仓库的标准 runner 通常不计费；私有仓库按分钟计。本报告按 109 次 run / 34 天 ≈ 3.2 次/天推算月成本，push 频率是估算；仓库可见性与计划未核验。
- **没有跑 E2E**。所有“修完能省 X 秒”都是基于源码结构与日志的算术，不是修完后的实测；实施时每项都要用同条件 A/B 复测（review-rules #2）。
