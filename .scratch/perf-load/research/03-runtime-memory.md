## Question

挑人 / 搜索 / 对决 / 结果四个相位的运行时成本：宽命中搜索（1000+ 命中）的主线程时长、DOM 节点与内存峰值、PWA 缓存占用（图片/字体）、海报 canvas 峰值；指出可优化项与风险。只测量，不改产品代码。

### 口径说明

- `search` 的 `debounceMs` 是 **input → MutationObserver**，包含产品里 120ms 的 `setTimeout`；`renderAfterMutMs` 是变更回调后的双 rAF（paint 窗口）。因此「纯渲染工作」≈ `debounceMs - 120ms`，与 longtask 的 startTime 对得上（wide 的 longtask 都在 ~120ms 起）。
- `performance.memory` 只有在 `--enable-precise-memory-info` 下才可用：默认 headless 里它恒报 `10,000,000`（实测分配 10M 个数组元素前后都不变），会给出完全错误的「峰值」。
- `performance.memory` **只覆盖 JS heap**；canvas backing store、已解码图片、Blink DOM 节点都不在里面。所以内存分三层给数：JS heap（实测）、canvas 像素（`width×height×4`）、解码图片（用 `PIL` 读实际文件尺寸 `w×h×4`）。
- longtask 只记录 >50ms 的任务；「总耗时」包含帧等待，两者不互相替代。

## Findings

按「收益 × 风险」排序（收益指主线程/内存，风险指视觉或离线承诺）：

1. **结果海报是唯一 ≥200ms 的单任务，也是内存峰值最高的相位。**
   40 人时 `draw 84–96ms + toDataURL 177–185ms` 合成 **282–306ms** 的单 longtask；16 人 228–234ms，7 人 184ms。canvas 只占 5.9–7.9MB，但 40 张 full 图同时解码约 **15.3MB（本次低分辨率样本）/ 47.6MB（全库平均）/ ~99MB（p90）**，再叠加 1.5–1.7MB 的 base64 dataURL。低端手机上这是最可能触发卡顿/内存压力的路径。`toDataURL` 的同步编码占了其中 82–185ms。

2. **80 张上限确实挡住了宽命中搜索的历史冻结，但仍留下 71–93ms 的 longtask。**
   1089 命中只渲染 80 张（39.9KB innerHTML、483 个 roster 节点），提示「1009 more」正确。成本集中在模板拼接 + 80 张卡的 HTML 解析/插入；headless 桌面 71–93ms，按移动端 3–5× CPU 估约 200–450ms。搜索的 `rosterView` 还在 `renderRoster`、`paintFilterSum`、`syncSelection` 里各算一次（1134 人 × `hay.includes`），但这部分不是主要成本。

3. **「全部展开」是 7.8k 节点的状态，整表重建约 195–197ms。**
   1134 张卡、7518 roster 节点、594.7KB innerHTML；全展开本身用 100 次点击累计 1.86–1.98s（每次点击后等一帧），最慢单次 39–53ms；在全展开状态下切一次筛选（现役→全部）整表重建 **195–197ms**，longtask **69–79ms**，JS heap 瞬时到 8.15–8.19MB（GC 后回 3.85MB，无泄漏）。页面总高 90,079px；24 次跳滚加载 175–179 张图，最大帧间隔 47.6–50.7ms，偶发 56ms longtask。默认首访只有 16 张卡 / 641 节点，不是问题；成本只在用户主动展开全部、且之后每次筛选/切档时重复支付。

4. **PWA 缓存按「条目数」封顶，和实际字节不挂钩。**
   600 条共享 thumb/full 的容量从 6.2MB（全 thumb）到 28.6MB（全 full），混合约 17.4MB；字体 500 条是防御性上限，正常只出现 2–12 条。quota 3.2GB、实际首访 1.8MB，**当前没有配额风险**；风险是缓存淘汰策略：600 张 full 会把大量 thumb 挤掉，离线名册出现坏图，而 `put()` 的配额失败是被 `catch (_) {}` 吞掉的（现有设计），不会有任何用户可见信号。

5. **对决相位没有可测的主线程问题。**
   进入对决 29–41ms 可见、50–83ms DOM 就绪；每题 209–214ms 中 160ms 是刻意的选择确认延迟，longtask 为 0。除非要改 UX，否则不值得为对决战做性能改造。

6. **内存没有泄漏信号，但 `performance.memory` 不是完整的内存画像。**
   搜索/全展开/结果在 GC 后都回到 ~3.1–3.9MB JS heap；峰值 4.0–8.2MB。canvas backing（5.9–7.9MB）、解码图片（2.8–15.3MB 实测，最坏 ~99MB）和 DOM 节点都在 JS heap 之外，只看 `performance.memory` 会低估一个数量级。

## Caveats

- **headless 桌面 Chromium + 本机 CPU**：绝对 ms 不能直接外推到手机；文中给了范围与中位数，移动端 CPU 通常慢 3–5×，内存也更紧。所有数字都是同一台机器、同一天、同条件两轮交替的结果（review-rules #2/#6）。
- **第三方字体被 abort**：这是为了让四个相位的运行时成本不被 Google Fonts 的 0.3–20s 网络抖动污染；代价是字体/布局与真实首访不同，`load` 也提前。字体本身的成本见 `01-first-visit.md`。
- **`performance.memory` 需要 `--enable-precise-memory-info`**：默认 headless 恒报 10,000,000，不可用；开启后也只覆盖 JS heap，且按 20ms 采样，可能漏掉 <20ms 的瞬时尖峰。canvas 像素与解码图片是 **`w×h×4` 估算**，不是浏览器实际 GPU/CPU 占用；不同浏览器可能用更紧凑的格式，估算偏保守。
- **全展开整表重建有一次未强制 GC 的运行测得 330ms**（同一动作、同一浏览器、不同堆状态）；最终表的 195–197ms 是另两轮在 `window.gc()` 后的稳定值。报告取后者作为可复现区间，但 330ms 说明堆脏时会更慢。
- **本次 40 人海报用的是 48g 前 40 个 id**，其中不少早期成员原图只有 160–400px 宽，所以实测解码 15.26MB 低于全库平均；全库平均 1.19MB/张与 p90 2.47MB 来自 1537 张 full 的实际尺寸，**不是**本次 40 人海报的实测值。
- **PWA 字体缓存两次运行差异大**（2 条 / 12 条）：取决于 SW 接管时机与 unicode-range 子集的请求顺序，不是稳定指标；图片缓存首访为 0 是预期（SW 接管前已加载的图片不会回填）。容量数字来自文件库存与规则，不是「把缓存填满」的实测。
- **搜索是页内 `value` + `input` 事件**，没有真实键盘/IME；120ms 防抖包含在 `input→paint` 里，纯渲染工作用 `debounceMs - 120ms` 与 longtask 交叉核对。
- **longtask 阈值为 50ms**；「无 longtask」不等于瞬时（例如全展开 100 次点击总计 1.9s，但每次任务多在 50ms 以下）。「整表重建 195ms + longtask 69–79ms」说明工作被拆成多个任务/帧，墙钟仍是 195ms。
- **没有跑完整 E2E 套件**；没有测离线、没有填满图片缓存、没有测分享链接冷启动的海报图片下载（分享结果页 40 人 full 图约 1.86MB，慢网下 `readyMs` 会显著变长）。
- **没有改任何产品代码**；脚本与 JSON 都在 `/tmp/opencode/`，仓库内只新增本报告。
