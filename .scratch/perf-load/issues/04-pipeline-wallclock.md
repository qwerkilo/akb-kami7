# 04 · 数据管线墙钟分解

- **Type**: research
- **Status**: resolved
- **Blocked by**: 无

## Question

增量跑 14–15 分钟的构成：旧站扫描、下载/压缩、数据阶段各占多少？哪些是限流地板、哪些是可并发/可缓存/可跳过？
给出可压缩上限与代价（Wayback 限流、重试、磁盘），不实施、不跑全量管线。

## Answer

完整证据与推导见 `.scratch/perf-load/research/04-pipeline-wallclock.md`。结论：

1. **14m08s 的实测构成**（2026-10-06，`pipe-conc.log` / 工单 08 的阶段表）：旧站扫描 **370.5s（44%）**、下载 **281.1s（33%）**、数据阶段 **145s（17%，官网 86.7 + 维基 32.6 + imageinfo 25.7）**、Commons 26.6s、压缩 3.9s、其他 ≈21s。同日第二次 15m32s，差异全来自网络漂移（数据阶段 2.4 vs 5.6 分钟）。
2. **下载的 4–5 分钟不是 FUSE stat**：是两个永久 404 的死快照在叠加重试（24 次请求 + 183s sleep）。`693cdee`（404/410 快失败）之后下载阶段应回落到秒级（本机实测 1338 次 orig stat = 0.40s，1535 次约 0.46s）。按 `pipe-groups.log` 推算，今天同数据状态约 **6m06s（推断，未实测）**；若 #5 真生效再降到 **≈5m27s**。
3. **限流地板**：Wayback 2 并发/0.2s（3 并发实测更慢，A/B 24.5/41.2s vs 5.9/6.5s）→ 48 次抓取 121–166s；48pedia 2 并发/0.5s（521 前科）；Commons 串行 + `pause=1.5`（429 会被误记「源里没有」）；helloproject 3 并发 → 70 页 54–120s。**已并发/已缓存/已跳过**的（详情页池、`_orig`、压缩 mtime、有图成员跳过、无缺图不扫描）都不必重做。
4. **⚠ 新发现的真缺陷**：性能 #5（`b4a3111`）实际是**空操作** —— `image_query_files` 拿 `(group, name)` 键集合去和**文件名**比较，永远不过滤；测试夹具喂的是 `{"a.jpg"}`，形状与生产不同所以假绿。每轮仍付 **25.7–80.2s（27 批）**。修复很小（按 `photo_skip.skips` 过滤 + 改夹具形状 + 修正进度分母）。
5. **继续压缩的候选**：A 修好 #5（省 26–80s，低风险）；B 旧站/Commons 负结果缓存（省 2m10–3m30，需 TTL 7–30 天并改 ADR-0023 #3，且绝不能缓存「查询失败」）；H 跳过重复 file-evidence CDX（8–12s）。三者合计可到 **≈2m50s–3m20s**。数据页 TTL 缓存（D）能进 1–2 分钟但违反 ADR-0023「数据照常抓」，只适合 `--fast` 调试开关。
6. **不建议**：Wayback 3+ 并发（实测更慢）、去掉 Commons 1.5s 节流、降低每团扫描预算（历史上有 5 人被误判「源里没有」）、优化压缩/FUSE stat（合计 <20s）、把 `_resolved.json` 当负缓存（会与文件脱节）、默认缓存数据页。
