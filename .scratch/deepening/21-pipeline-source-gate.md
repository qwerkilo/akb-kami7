# ㉑ 数据管线的必需源门：名册塌了就不许写盘

- **日期**：2026-09-29
- **来源**：架构扫描候选 7（48G 侧缺「必需数据源」门）
- **性质**：补上等爱侧早就有的那道防线（记忆 #174）——48G/坂道 侧一直没有
- **测试缝**：Python 解析纯函数（`scripts/test_fetch_members.py`）

## 隐患链（取证自当前代码）

```
members = merge_members(load_rows(fetch_page))   ← 48G/坂道 侧无门
… collect_paths（下载）→ compress_members → warn_missing_images
  prune_unused({m["id"] for m in all_members}, …)  ← 把不在新集合里的每个文件 os.remove 掉
  write_members_js(sections, …)                    ← 写入被截断的名册
```

只要 48pedia 抽到一个错误页、wikitext 格式变动、或代理把 HTML 截断，`members` 就是空或残缺 → `prune_unused` **把不在新名册里的每个图片文件删掉**（48G/坂道 侧 1338 人的图）、`members.js` 只剩等爱成员，程序只打印一行 `removed N` 就跑完了。等爱侧在 v3 批次已经有 `raise SystemExit`（「为避免误删已有数据与图片，本次不写入」✓），48G/坂道 侧一直没有——而这一侧人数是那侧的 30 倍。

## 改法

1. `roster_problems(new_members, baseline)` —— **纯函数**，返回问题描述列表（空 = 正常）✓
2. `read_baseline(root)` —— 读盘上已有的 `members.js` 当基线（`{groups, total}`）✓；读不到（首次生成）返回 `None` → 无可比基线，放行 ✓
3. 判据两条：① 总人数 < 基线的 **60%**（`ROSTER_DROP_LIMIT`）；② **基线里的某个团体这次一个成员都没解析到** ✓（这一条能在总数不掉的情况下抓住「某团解析崩了」✓）
4. 门放在 `merge_members` 之后、**第一个破坏性动作（下载）之前** ✓
5. 逃生阀 `--accept-drop`：放行但打印醒目警告并写进 stdout ✓（「确认是上游真的少了人」才用 ✓）
6. 首次生成没有基线 → 放行 ✓；人数**增长**永远不会触发 ✓

为什么阈值取 60%：给正常毕业带来的自然收缩足够余量（等爱现役 33+毕业 4、48G 每年自然减员 ✓），同时「整页失败」「某团解析崩」都远在这个幅度之下 ✓。阈值是 `ROSTER_DROP_LIMIT` 一个常量 ✓ 可改 ✓。

## 审查打回过一次（`B1` 致命）

基线 `members.js` 里含等爱三团，而 `load_rows` 只喂 `GROUP_ORDER` 的 10 团 → 「团体消失」判据**恒非空 → 每次合法刷新都会中止**（比 fail-open 更糟：逃生阀变成每次必敲的常规操作）。**我的测试没看见**，因为 fixture 只产 48G 分段、把口径错位自己抵消了。现已把 `read_baseline` 限到 `GROUP_ORDER` 内的团体（真实基线 1338 人 / 10 团 ✓），并补「基线含等爱分段时健康 48G 名单必须放行」的测试 ✓。

审查同时指出并已修：`read_baseline` 对畸形产物抛未捕获 `AttributeError`（补形状校验 ✓）、基线读不出来时**静默放行**（现在会打印「本次不校验名册规模」✓）、死参 `new_total` 删除 ✓、逃生阀警告从 stdout 移到 stderr ✓、模块 usage 与管线文档补 `--accept-drop` ✓。

**新加的逐团下限**（`ROSTER_GROUP_LIMIT = 0.5`）：审查指出「某团腰斩但团还在」抓不住（AKB48 400→200 放行 ✓ 而 prune 照样删掉那半团全部图片 ✓）。逐团下限与总数阈值同源，**这比 grill 里批准的判据更严**（多一条阻塞条件）——真解散一个团需要 `--accept-drop`，那正是这把钥匙的用途。已实测（基线每团 100 人、AKB48 掉到 40 → 精确命中一条 ✓）。
