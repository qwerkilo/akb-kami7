# 深化⑰：海报的「照片或占位」收成一个绘制点

来自架构扫描的 Top recommendation（`/tmp/architecture-review-20260929-003318.html` 候选 1）。

## 症状（实测，不是推断）

用假 ctx 跑「全员无照片」（`images: null`）× 四样式 × 三档，统计占位底色的 `fillRect` 次数：

| 样式       | 7     | 16    | 40               |
| ---------- | ----- | ----- | ---------------- |
| a 金字塔   | 7     | 16    | 40               |
| b 杂志     | 7     | 16    | 40（**无首字**） |
| **c 榜单** | **4** | **0** | **0**            |
| d 拼贴     | 7     | 16    | 40（**无首字**） |

c 之所以是 4/0/0：领奖台与紧凑榜行只有 `if (images[i]) cover(…)`、**没有 else**。也就是**40 档选榜单样式、离线出图时，40 格全都没有脸**（名次与名字还在）——复核实测：父提交 c/40 的占位 `fillRect` 为 **0**（领奖台那 3 格也只有 `if` 没有 `else`），比扫描报告里「37/40」的说法更彻底。这正面撞上 `CONTEXT.md` 的「离线可用：照片按浏览历史」与 ADR-0016 后果第 2 条。

现有测试**结构上抓不到**：四组海报用例都用 `fakeImgs`（非 null），唯一的占位用例把样式集合写死成 `["a","b","d"]`——等于给 c 立了碑。

## 收口

`poster.js` 新增 `photo(ctx, T, im, box, name)`，五个消费点全部走它：`slotCard`、杂志 hero、领奖台、榜单紧凑榜行、拼贴拍立得。

- 只负责「有图就 `cover`、没图就底色 + 名字首字」；**圆角与裁剪仍归调用点**（拼贴的圆角画在 `rotate` 变换里，搬进 module 就要引入变换感知，接口会变宽而收益没有）。
- 首字字号 `min(框高 / 3, 96px)`（实测封顶的咬合点）：a/7 三档框高 288 / 363 / 523 → 未封顶是 96 / 121 / **174**；b 的 hero 框高 641.6 / 784.9 / **1082.7** → 未封顶是 214 / 262 / **361**（巨字会压掉名次角标）。领奖台框高 278–348（/3 = 93–116，本来就在 96 上下）。低于 6px 只留底色（40 档榜单紧凑行是 34.77px → 12px，16 档 58.67px → 20px；`44*k` 是上限不是实际高）。
- `box` 用对象而不是四个位置参数：5 个调用点里有一个在 `translate + rotate` 之后用相对坐标，对象让「一个框」这件事读得出来。

## 红回路

- **红**：`test/poster.test.js` 的新测试「全员无照片时每个位置都有占位（四样式 × 三档，占位与首字）」——实现前 `c/7` 报「占位底色应画满 7 格，实际 4」、`d` 报「未用注入的 placeholderInk」。原来那条占位测试里的 `["a","b","d"]` 豁免同时删掉，字色断言从「只有 a」放宽到「每样式都画首字」。
- **绿**：同一条测试四样式 × 三档全绿；`npm test` JS **138** / Python 88。
- **两轴复审后把断言加严**（原先只做存在性断言，等于没有守卫）：① 夹具换成**首字互不相同**的名字——`people(n)` 的「成员1/成员2/…」首字都是「成」，那种情况下「首字顺序」与「下标错位」都测不出来；② 首字断言从「用过字色」改为**多重集合与成员首字相等**（用集合而非绘制顺序：绘制顺序是版式决定，a/7 与 c/7 都是「中间先画」）；③ 补**字号落在 0–96 的上界断言**；④ 用例表从 7 组补满 4 样式 × 3 档 = **12 组**。
- **判别力实证**（五个变异，每个都让新测试变红）：领奖台取 `members[0]`、紧凑榜行取 `members[0]`、拼贴取 `members[0]`、去掉 96 封顶、把早退阈值提到 20px。

## 等价性证明

有照片时 `photo()` 只做 `cover`（早退），所以**在线路径的绘制调用序列必须逐条不变**：4 样式 × 3 档的调用条数收口前后完全一致（a 316/703/1686、b 287/674/1706、c 257/299/635、d 4370/6089/5745）。

## 代价与遗留

- **a 样式的占位首字在大卡上收窄了**：7 人档冠军卡照片区 523px，原来 `/3 ≈ 174px`，现在封顶 96px；中间两张 363 → 121 → 96。视觉核对过（`/tmp/opencode/ph-check.png` 五张实拍），与 hero/领奖台的观感更一致。这是 Q1 明确批准的封顶，不是副作用。
- **a/16 与 a/40 的无名字行现在也有了首字**（`PYRAMID_NAMED_ROWS` 之后的行本来不画名字）：方向是改善——那些格的首字成了唯一的身份线索，但属可见变化，记在这里。
- **b 的 hero 占位是「一大块底色 + 一个 96px 的字」**，在 1080 宽的冠军位里略显空。若日后觉得空，把封顶按「框宽的 12%」再调（一个常数）。
- **首字对比度 2.11:1**（`placeholderInk #9aa0b0` on `placeholder #e4e7ee`），连大字号 AA 的 3:1 都不到。这是**继承债**：名册 SVG 占位（`core.js`）用的是同两个令牌、同一对值，classic 皮肤也没有单独覆盖（实测两套皮肤同值）。本轮把它放大到 96px × 四样式 × 三档，曝光面变大。96px 下实拍仍可读；改令牌会同时动名册与海报两处视觉，超出本轮范围。
- **拉丁字母首字偏弱**：`miray` / `Stefi` 这类小写开头的名字，首字是 x-height 高度（7–10px），在 40 档榜单紧凑行里比汉字弱一档。1375 人里 9 人如此。不做转写（站内成员名与名册保持原文）。
- **b 的 hero 占位是一大块底色 + 一个 96px 的字**，在 1080 宽的冠军位里略显空。若日后觉得空，把封顶按「框宽的 12%」再调（一个常数）。
- 榜单紧凑榜行的占位首字很小（框高 44px → 15px），但与缩略图尺寸成比例 ✓。
- 假 ctx 仍看不见这些占位的**几何**是否好看（那是候选「海报几何」的范畴，已归档）；本轮靠实拍核对。实拍只覆盖 12 组里的 5 组（a/7、c/7、c/16、d/7、b/7），**恰好不含 40 档 c**——那组靠假 ctx 的计数与两轴各自独立跑的真实画布（每格墨色 86px、字形 12×11）核对。
