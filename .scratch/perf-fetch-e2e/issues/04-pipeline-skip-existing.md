# 工单 04：管线跳过已有照片 + `--refresh-photos`

- **Status**: partially-resolved（跳过已实现并验证；判据 1 的耗时未达标 —— 见实现记录）
- **Blocked by**: 无

## 目标

**增量跑为默认**：照片解析只服务**没有站内照片**的成员（判据 = `img/full/<id>.webp` 与
`img/thumb/<id>.webp` 都在且非空 —— 与 `img` 标志同一真值源）；**数据（官网/维基）照常抓**。

新增 `--refresh-photos`：忽略「已有照片」的跳过与 `_resolved.json` 缓存、重解析所有照片。
`--force` 语义不变（只重下载 + 重压缩）。

## 判据（可证伪）

1. **增量跑实测 ≤8 分钟**（2026-10-05 的基线是 30–100 分钟；记录实测数字）。
2. 跑前跑后 `img` 标志**逐一相同**（无丢失）；缺图名单仍是那 12 人。
3. 12 个缺图者**每轮仍被尝试**（日志里能看到它们的解析/失败记录）。
4. `--refresh-photos` 实测能重解析：对一个**已有照片**的成员，跑 refresh 后其照片被重新解析
   （日志/URL 变化可见，`_resolved.json` 被重写）。
5. 变异验证 ≥2 全杀（例：把跳过判据改成「任一文件存在」→ 判据 2 应红；把 `--refresh-photos`
   接成 no-op → 判据 4 应红）。

## 实现记录（2026-10-05）

**实现**：`photo_skip_predicate`（判据 = `img/full` + `img/thumb` 都在且非空；以**上一轮
members.js** 的 name+group → id 为桥 —— id 规则依赖全局重名顺序，不能从单个成员重算）+
`photo_skip_for`（`--refresh-photos` → None）+ `default_loaders`（把 skip 与缓存开关接到
两个 loader）；两个 loader 各收 `skip_photo`（早安在链首过滤一次、等爱在 `_needs_photo`）。
`parse_args` 加 `--refresh-photos`（与 `--force` 职责分明）。

**测试**：7 条新测试（判据 4 条 + 参数 3 条 + 接线 3 条，含「`--refresh-photos` 接成 no-op
应红」）全绿；变异 3 个全杀（任一文件存在 / refresh no-op / 早安不过滤）。

**实测（2026-10-05 23:47 起，增量跑）**：**跑到 36m55s 仍没结束**（照片阶段卡了 28+ 分钟，
被手动终止）—— **判据 1（≤8 分钟）不成立** ✗。

**根因（实测 + 读码）**：跳过只省掉了**按成员**的解析，省不掉**旧站扫描**：
`resolve_old_site_photos` 对「**有任何一个缺图成员的团**」都要枚举该团前缀下的全部候选 URL，
每 URL 试最早 3 个快照，每团预算按 **URL 数**算（当前 `max(70, 900//团数)` → 每团可达
180 个 URL = 540 次抓取 ✗）。12 个缺图者散在 **5 个团**（モー娘。3 / ℃-ute 3 / アンジュルム 3 /
つばき 1 / OCHA 2）→ 扫描照旧跑到全局上限 900 次抓取 ✗。
另一个放大器：这 12 人的 `join` 全是空的（源里没有）→ 在籍期**没有下界** → 几乎所有快照
都「在籍期内」→ 候选 URL 几乎不过滤 ✗。

**待决（见 Comments）**：把每团预算从「URL 数」改成「**抓取次数**」并随缺图人数缩放
（例：`max(30, 15 × 缺图人数)`），配合工单 06 的并发 → 预计增量跑 5–8 分钟。

## 注意

- **判据是站内文件，不是缓存**：缓存只覆盖早安，且会与文件脱节（有 URL 但下载失败的人）。
- 注入方式：`fetch_members` 知道 id 规则与目录（`img/full` / `img/thumb`），把
  「该成员有没有站内照片」的判定**作为回调注入两个 loader**（早安 + 等爱），
  不要在 loader 里各抄一份 id 规则。
- 等爱链不需要单独做缓存 —— 本跳过天然覆盖它（第一轮 grill 里那条推荐被取代）。
- 冻结的语义写进 `CONTEXT.md`（增量跑 / 全量刷新）与 `docs/adr/0023-photo-freeze.md`。
