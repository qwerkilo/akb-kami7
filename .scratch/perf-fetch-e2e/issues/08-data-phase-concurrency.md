# 工单 08：数据阶段并发（官网详情 + 维基 + 48pedia）

- **Status**: ready-for-agent
- **Blocked by**: 无

## 背景

工单 04 的增量跑复测 **19m54s**，其中 **~10–12 分钟是数据阶段**（纯网络、全部串行）：
官网 7 个列表 + 70 个详情页、11 个 Wikipedia 条目、48pedia 11 个来源页 + ~27 次
`imageinfo` 批量查询 —— 这些请求**彼此独立**，串行纯粹是历史写法。

照片阶段（工单 04/06）已经压到 ~5 分钟；**数据阶段是现在的地板**。

## 决定

1. 三个 loader 的**独立请求**进小线程池：详情页（70 + 33）、维基页（11 + 3）、
   48pedia 来源页（11）与 `imageinfo` 批次（~27）。
2. **按主机限流**：`helloproject.com` 与 `ja.wikipedia.org` 各 2–3 并发 + 最小间隔；
   48pedia 1–2 并发（WAF/521 前科，见 `docs/agents/data-pipeline.md`）。
3. 结果按**确定性顺序**应用（解析顺序不变、产物逐字节可比）；失败仍走各 loader 现有策略
   （官网 empty / 维基 raise|empty / 48pedia 重试）。
4. 请求节流与重试沿用现有的（`get(retries=8)`、`pause`），并发不改变单请求语义。

## 判据（可证伪）

1. **数据阶段实测 ≤5 分钟**（当前 ~10–12 分钟；记录前后数字）。
2. 产物**逐字节不变**（同一网络状态下 `members.js` 与优化前相同；不同网络状态时
   至少「成员数 / img 标志 / 分段形状」三项一致）。
3. 并发数有单元测试（注入假 fetch + 假时钟：并发不超过上限、间隔不足时排队、
   某请求失败不拖垮整批）。
4. 变异 ≥2 全杀（例：去掉限流 → 测试应红；把确定性顺序换成「完成即写」→ 判据 2 应红）。
5. 不触碰照片阶段（工单 04/06 已定的预算与限流）。

## 注意

- 三个 loader 的装配逻辑（合并、去重、跨团）**保持串行**，只并发**取数**：
  先并发抓进 `{url: text}`，再按原顺序喂给现有解析。
- 测试注入的 `fetch` 是同步可调用对象 —— 并发封装要允许注入（否则测试全变联网）。
- 48pedia 的 `load_rows` 走 `wiki.get`（默认 4 次重试），与管线边缘的 8 次重试不同源；
  并发时别把两套重试叠成 32 次。
