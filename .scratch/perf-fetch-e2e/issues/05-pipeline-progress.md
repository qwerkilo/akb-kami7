# 工单 05：管线进度（阶段行 + 心跳）

- **Status**: resolved
- **Blocked by**: 无

## 目标

管线跑起来能直接回答两个问题：**到哪一步了**、**在动吗**。

1. **阶段行**：每个耗时阶段开始与结束各一行 —— 阶段名、总数、命中数、耗时。
   至少覆盖：48pedia、三个 loader 的官网/维基抓取、旧站扫描、Commons、下载、压缩。
2. **心跳**：阶段进行中每 ~10s 一行 —— `已完成÷总数`、**速率（次/分）**、
   **距上次成功的时间**（`上次成功 32s 前`）。
3. 输出**实时**（`print(..., flush=True)`，不依赖 `-u`）。

## 判据（可证伪）

1. 跑一次（可用 `--no-dl` 或小规模）输出含阶段行与心跳；**心跳间隔 ≤15s**。
2. 心跳含速率与「上次成功」时间（不是只有累计数）。
3. 人为制造一个慢源（如注入一个 5s 才返回的 fetch）→ 心跳能显示「上次成功 Xs 前」在增长，
   而速率在掉。

## 实现记录（2026-10-06）

**实现**：`scripts/progress.py`（`stage()` 上下文管理器 + `Stage.tick(ok=…)` +
模块级 `tick()` 转发到最内层阶段 + `enable()`；默认**静默**，`fetch_members.main` 打开）。
接线：48pedia 来源页 / 48pedia 图片 URL / 等爱（官网+维基）/ 早安（官网+维基）/
旧站扫描 / Commons / 下载原图 / 压缩 —— 八个阶段，各自的循环逐项 `tick()`。

**测试**：`scripts/test_progress.py` 7 条（静默、阶段行含名字/总数/耗时、心跳 ≥10s 才开口、
速率与「上次成功」反映真实值、失败计数、模块级 tick 进最内层、无阶段时 no-op）。
其中一条的**期望值我一开始写错**（把第 13 次 tick 的心跳写成 12/200；实际 13/200 ·
8 次/分 —— 按时间线算得），按真值改正。

**真跑冒烟**（假 fetch 每次 1s + 真 `_resolve_old_site_groups`）：

```
▶ 旧站扫描（共 60）
  … 旧站扫描 10/60 · 60 次/分 · 上次成功 0s 前
  … 旧站扫描 60/60 · 60 次/分 · 上次成功 0s 前
✓ 旧站扫描 60 项 · 用时 60.0s
```

心跳间隔 10s（≤15s ✓）、速率正确（1 次/s = 60 次/分）、总数 = 各团预算之和。

## 注意

- 心跳行数要可控（一小时 ≈ 300 行）；**阶段切换行**与**心跳行**前缀不同，便于 grep。
- 别把进度写到 stderr 之外的地方：现有日志靠 `> /tmp/opencode/pipe.log 2>&1` 收集，
  两者都会进日志即可。
