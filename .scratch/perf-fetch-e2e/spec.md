# Spec：跑得更快、看得见进度（fetch 管线 + E2E）

- **Status**: ready-for-agent
- **依据**：2026-10-05 四轮 grilling（本会话，用户逐轮确认）
- **目标**：两条耗时的长回路都变短，并且执行时**有进度可看**（不靠外部工具判断假死）

## 事实基线（优化前，实测/逐行计数）

**fetch 管线**

- 耗时几乎全在**旧站快照扫描**：`resolve_old_site_photos` 最多 900 次抓取，每次抓取前
  `sleep(1.5)`、全串行 → 光睡觉 22.5 分钟，加 Wayback 真实响应 2–5s/次 ≈ **50–100 分钟**。
- 下载与压缩**已经**跳过已完成的工作（`download()` 先查文件存在、6 线程；压缩跳过未过期）——不是瓶颈。
- 缓存 `_resolved.json` 只服务早安 loader、只跳照片解析；等爱链无缓存。
- 1.5s 节流是为 **Commons 的 429** 引入的，却套在 Wayback 上（Wayback 的实测问题是 521 偶发）。
- 数据抓取（官网 103 详情 + 14 个 Wikipedia 页 + 48pedia 38 请求）约 2–5 分钟。

**E2E**（四套件**串行**实测约 25 分钟，2026-10-05 22:45→23:11）

| 套件         | check   | 页面加载 | 等待合计 | context |
| ------------ | ------- | -------- | -------- | ------- |
| `e2e`        | 245     | 30       | ~90s     | 14      |
| `e2e:v5`     | 54      | 6        | ~16s     | 2       |
| `e2e:pwa`    | 43      | 11       | ~10s     | 6       |
| `e2e:header` | 72 状态 | **72**   | **126s** | 36      |

- 四脚本端口互不冲突（8765/8777/8781/8861）、pwa 用独立 tmp 目录 → 可并行。
- 硬约束是**内存**：本机 15GB，可用 <3GB 时单次导航要 30s（`scripts/preflight.mjs`）。
- 浪费点：header 每状态先 goto 再 reload（只为拿 origin/localStorage）；`e2e.cjs` 的 v2 块与
  v5 先加载一次又立刻 clear+reload（首次加载被丢弃）。

## 决定（grilling 逐轮确认）

1. **两边都做，E2E 先行**（它是高频开发回路）。目标：E2E 全量 ≤5 分钟；管线增量跑 ≤8 分钟、
   全量刷新 ≤20 分钟。
2. **E2E 并行**：新增 `npm run e2e:all`（内存感知并发：≥6GB → 4、≥3GB → 2、否则串行）；
   四条既有命令语义不变。`e2e.cjs` 的块**不拆进程**（留作后备）。
3. **E2E 砍浪费**：header 的 goto+reload 合一；删掉 v2/v5 被丢弃的首次加载。
   ~~`ready()` 不动~~ → **被工单 07 取代**：画像发现 `ready()` 的等待恒假、每次白烧 120s
   （9 次 = 18 分钟），改成「视口内图片 + 字体」（见 07 的记录）。
4. **管线跳过已有照片**（增量跑为默认）：照片解析只服务**没有站内照片**的成员
   （判据 = `img/full` 与 `img/thumb` 都在且非空，与 `img` 标志同一真值源）；**数据照常抓**
   （新成员/改名/毕业必须能进来）。
5. **全量刷新是显式开关**：`--refresh-photos` 忽略跳过与缓存、重解析所有照片；
   `--force` 语义不变（只重下载 + 重压缩）。
6. **管线并发排在跳过之后**：旧站扫描段上线程池 + **按主机限流**；429/521 自动降速（连续
   成功后退回）；结果按确定性顺序应用。~~Wayback 3 并发/0.5s、Commons 与 ja.wikipedia 1/1.5s~~
   → **被工单 06/08 的实测取代**：Wayback 实测 2 并发最快（3 并发被限流反而更慢），
   官网/维基 3 并发；现行值只看 `fetch_pool.HOST_LIMITS`。
7. **进度**：管线打阶段行（总数/命中/耗时）+ ~10s 心跳（已完成÷总数、速率、**上次成功 Xs 前**）；
   E2E 打块头 + 超过 5s 的等待行；并行 runner 每套件一行开始/结束、失败聚合尾部输出。

## 时长目标的最终说法（2026-10-06 收口）

- **E2E 全量并行**：26 分钟 → **4m31s–5m12s**（跨轮波动）。判据「≤5 分钟」基本达成
  （最坏一次 5m12s，差 12 秒）。
- **增量跑 ≤8 分钟**：**未达成** —— 实测 14m08s / 15m32s。数据阶段已降到 ~2.4–5.6 分钟
  （工单 08 ✓），剩余地板是**旧站扫描 ~6 分钟**（工单 06 后）+ **下载 ~4.7 分钟**
  （多数命中 `_orig` 缓存，耗时在 FUSE 的 stat）+ 网络当时的快慢。跨轮数字不能当基准
  （同日两次的数据阶段差了 2–4 倍）。
- **全量刷新 ≤20 分钟**：**从未实测**（`--refresh-photos` 只做了单测 + 变异）。
  要真测就是一次全量照片扫描（~900 次抓取的上限、半小时级）—— 记录为未实测。

## 验收（可证伪）

- E2E：**check 数守恒**（245/54/43/72 一个不少）+ 四套件各**连跑两次全绿** + 实测墙钟前后对比。
- 管线：增量跑实测 ≤8 分钟；`img` 标志与跑前一致（无丢失）；12 个缺图者每轮仍被尝试；
  `--refresh-photos` 实测能重解析；并发后**结果与串行一致**（同 fixture 下 `urls` 相同）。
- 进度：跑一次就能看到心跳/块头/长等待行，且心跳间隔 ≤15s。
- 全程：`npm run check` 全绿；变异验证按各工单要求。
